# 本机目标缓存：离线研究（2026-10-18）

> 本文保留实现前研究状态。0.3.0现已实现主武器缓存测试候选，现状及剩余限制见
> [后端审查](CACHE-BACKEND-REVIEW.md)；不是旧入口的重发。

已复现旧版“不起效”的一个独立缺陷，并找到无需改写游戏指令的候选方向。
这里只证明原生消费者的行为；尚无新的游戏运行时实现或测试包。
0.2.5的仅入口退出仍然没有定位首个故障，以下缺陷不能解释那次退出。

## 候选与保留目标不是同一种记录

当前Steam build 25480438的两种指针必须分开：

| 交互者runtime字段 | 指向对象 | 可证实的内容 |
| --- | --- | --- |
| `+0x08`起的256个候选指针，数量`+0x808` | 12字节payload | `u32 entity, u32 zone, f32 score`；地址为Interactable管理器`+0xE000 + index*12` |
| `+0x00`保留目标指针 | 20字节空间记录 | 前12字节为位置，`+0x10`为上述payload的index。不能将前8字节当entity/zone |

生产者证据：`0x9A0B10`从管理器`+0x14018`取空间记录数组，按20字节步长
取记录；`0x9A0B67`读空间记录`+0x10`，`0x9A0B80`算出payload地址。
`0x9A268C`将payload地址放进候选数组。另一条链在`0x9A2271`重新载入空间记录，
`0x9A264C`保存最高分对应的空间记录，最终`0x9A286B`写入交互者`+0x00`。

消费者证据：`0x9A49E0`查询保留目标时，读取它的`+0x10`，再返回对应payload。
手动交互入口`0x9A4750`也这样解析，并不读取候选数量或数组；满足原生可用条件
后，`0x9A4981`把payload中的entity/zone传给`0x979570`请求边界。

撤回的0.2.4在删候选时比较“保留指针 == payload指针”，随后又把保留指针
送入payload分类器。真实空间记录的坐标位模式被误读成entity/zone，分类通常失败
并放行，于是保留的主武器仍可能被提交。旧测试把保留指针直接设成payload，
没有覆盖真实布局。保留旧字节，不修改它来重新发布；新增反例明确记录该缺陷。

`0x97B7F0`读取的runtime区域`+0x60`是原生可用条件，不能用它的偏移去套
FileDiver模板结构的AutoInteract字段。自动交互的检查在`0x9A378F`读取模板
区域`+0x80`；模板区域步长0x88，runtime区域步长0x68，二者也必须分开。

## 正常帧存在数据处理窗口

同一版本的保留EXE和game.dll代码给出下列正常路径：

```text
EXE 0x689AF0
  -> 0x689B98: 调用Lua全局update（名称来自EXE+0x1678150）
  -> 0x689BAF: 尾调用0x60030
       -> 0x60137: 调用插件API +0x68
          -> game.dll 0x4EE6C0 -> 0xAB5000 -> 0x571250
               -> 0x5731CA: 角色更新0x829E90
                    -> 0x82A4A0 -> 0xA3E620
                       -> 0xA3E985 -> 0xA61F80
                          -> 0xA622E5 -> 0xA62310
                             -> 0xA624BF -> 手动交互0x9A4750
               -> 0x573281: 交互者更新0x9A3440
                    -> 0x9A35F6: 刷新候选0x9A05B0
```

游戏插件API基址`0x37CEB10`，注册在`+0x68`的函数确为`0x4EE6C0`。
Lua调用助手用globals index -10002查找`update`，最后经过lua_pcall执行。
该全局表索引与[Lua 5.1官方头文件](https://www.lua.org/source/5.1/lua.h.html)一致。
7个保留IAT指针与本机已安装、SHA固定的lua51.dll导出表对应同一对齐模块基址；
这只是读取DLL导出目录，未加载DLL或接触运行中的进程。

因此正常帧中，Lua回调可在角色读取上轮目标之前修改缓存。post事件本身仍不能
取消已发生的拾取；可行性来自**下一次请求消费的缓存**，并非更改事件payload。
不要求在原生收集函数和它的返回点之间插入跳板。

这个顺序不覆盖所有路径：`0xFDAEE0`也会调用组件更新`0x571250`，尚未证明它的
间接调用条件；其他插件在Lua/原生阶段间的行为也未覆盖。不能据正常帧路径宣称
所有帧、加载和增援都已验证。

## 实际完成的离线验证

`tests/fixtures/cache_consumers.json`包含53条小指令证据、3个消费者片段共1055字节。
`verify_cache_research.py`核对指令、调用目标、模块、空间记录区别和回调绑定；
显式提供保留capture后，核对3个完整本地section的SHA及57处片段/字符串。
完整section和DLL不进入仓库。

`tests/test_cache_consumers.py`的8项测试使用Unicorn执行保留的原生查询、手动
交互及runtime可用条件消费者，外部模板解析、特殊交互前置处理和请求函数为模拟边界：

- 撤回版仍能从数组删除主武器，但正确布局的主武器保留目标仍到达请求边界。
- 即使候选数归零，保留目标依然能发出该请求。
- 保留指针归零后，这条手动路径不再请求目标。
- 仅替换指定交互者的8字节保留指针，原生请求改为支援武器；区域0、1、7均一致。
- 其他交互者的行和所有指令字节保持原样；非本机拥有的角色被原生消费者拒绝。
- 被改动的证据和不存在的capture被拒绝；只读CLI不会创建交付目录。

“其他行未改变”只证明模拟中的写入范围，未完成房主/客机验收。
请求边界之后的真实换枪、网络处理及任务稳定性均未模拟。

## 下一步实现约束

先做必要的只读状态验证，再加入数据写入：

1. 每帧重新用本机avatar网络ID、descriptor实体和所有权解析当前交互者；不能缓存
   上一条命或上一次manager分配的地址。候选类型1及同位置类型3必须实际被观察到。
2. 对保留空间记录、payload与实体/区域作双向验证；替代目标必须取自本机当前候选，
   验证类型、可用状态、手动交互条件和空间记录映射。不得把payload直接写作保留指针。
3. 证明销毁、空间记录移动和交互者数组压缩时的处理。已有`0x9A3D40`会按空间索引
   清除保留目标，但它的注册与所有触发条件尚未证明；`0x9A4AB0`会搬动整条0x880行。
4. 证明额外世界更新入口不会在过滤和手动消费之间覆盖缓存；不以轮询频率替代顺序证明。
5. 关闭时停止改写，让下一次原生刷新恢复选择；不恢复跨帧保存的旧裸指针。
   不触碰候选payload、共享模板、世界武器启用位或任何游戏指令。
6. 此路径首先解决手动拾取。配置为AutoInteract的区域会在原生候选刷新内提交，
   仅修改保留目标不能拦它；样本等剩余选项是否走该路径必须逐项确认。其他五个
   选项的完整覆盖及来源观察仍需单独设计，不能标记全部完成。

发布策略仍为withdrawn/failed，打包仍禁止。离线“可替换目标”的反例不是可安装修复版。
